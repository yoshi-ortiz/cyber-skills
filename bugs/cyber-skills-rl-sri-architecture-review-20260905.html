Read-only architecture review

Compass, evidence loop, and safe self-improvement

The current feature compass is a credible bounded-control workflow, not reinforcement learning. Its strongest property is an explicit authority chain from Item to Shot to human verdict. Its weakest property is that roadmap selection, observation, proof, context admission, and future learning are presented as one story even though they have different owners and trust levels.

Architecture verdict

Promising seam, incomplete depth

repo_context.py next is a useful facade, but callers still need to understand roadmap fields, Shot lifecycle, token profiles, proof gates, and feedback states.

Language verdict

Evidence loop, not RL

No online policy update, reward model, credit assignment, or automatic parameter change exists. The implemented loop is deterministic control plus recorded human feedback.

Safety verdict

Good guards, two open risks

Acceptance authority and negative outcomes are protected. Privacy retention policy and deterministic extraction of corrections remain underspecified.

System map

The map uses the repository glossary. Repo-Dev Context owns Items and the Burndown. Tokens QA owns Shots. Design-Inference Context is only proposed as compiler input. The optional learner remains development-only.

Findings

Strong
keep

1. The Item to Shot authority chain is the right seam

Genesis parses and selects managed Items. Tokens QA records immutable Shot attempts and accepts feedback only through an explicit write command. Repo Context joins these two interfaces and refuses DONE when the latest item-linked Shot is not accepted, has a veto, lacks L2 proof, or has changed proof artifacts. This is real locality and leverage.

Evidence: first/genesis/scripts/compass.py, check/tokens-qa/scripts/tokens_qa.py, tools/repo_context.py.

Strong
narrow

2. “Reinforcement learning” overstates what exists

The implemented system has no learned policy and performs no training. It records outcomes, computes deterministic next actions, and permits a human to revise an instruction or test. Call this the feature evidence loop or attempt feedback loop. Reserve offline learning-to-rank experiment for the development-only learner in R-50. Reserve safe self-improvement for the governed review procedure, not a runtime capability.

Evidence: docs/SPEC/FEATURE_COMPASS.md lines 27 to 30; docs/SPEC/INFERENCE_CONTEXT_COMPILER.md lines 111 to 123 and 146 to 151.

Strong
safe

3. Acceptance cannot be fabricated through the public interface

New Shots begin pending. Feedback fields are independent. Advisory text classification writes nothing. Silence remains pending. “Good but fix X” fails. Closure requires explicit accepted status and proof. Synthetic flow tests demonstrate these mechanics without touching project state. This is evidence of control behavior, not evidence of user satisfaction or lower token cost.

Evidence: check/tokens-qa/SKILL.md lines 15 to 29 and 69 to 110; tools/test_compass_flow.py.

High
open risk

4. Local and dev-only is not yet a privacy contract

Shot records can contain the complete request, user corrections, paths, model metadata, and artifact hashes. The specs say records remain local and dev-only, but they do not define consent, redaction, retention, deletion, export, filesystem permissions, or secret scanning. “Privacy-safe local records” is therefore an aspiration. A safe contract should minimize stored text, allow caller-supplied redaction, define retention, and keep records out of publication and version control.

Evidence: docs/SPEC/SHOT_OBSERVATION.md; check/tokens-qa/scripts/tokens_qa.py lines 118 to 160; compiler outcome record lines 99 to 110.

High
replace judgment

5. The small-model entrypoint still asks the model to join too much

repo_context.py --json next returns one Item and latest observations, which is the correct shape. Yet the agent must still interpret free-text Scope and Proof, decide whether the user has corrected or accepted, decide which files form admitted context, and reconcile duplicate prose in root CONTEXT, Genesis, Feature Compass, Tokens QA, and the compiler contract. The compiler spec makes “parse the latest user request” part of a deterministic program without defining a deterministic grammar. That step cannot be reproducible as written.

Contamination paths: root CONTEXT.md Feature burndown; first/genesis/SKILL.md Compass; check/tokens-qa/SKILL.md; R-50 contract lines 55 to 80. Repo-Dev records such as BUGS, GOAL, SPEC, QA, CHANGELOG, and .audit are hazardous when loaded during Design-Inference.

Medium
deletion test

6. Several contracts describe the same policy

The same rules about explicit acceptance, preserved corrections, token honesty, and no automatic prompt mutation appear in at least four documents. Deleting any one of these paragraphs would not remove behavior because the executables and tests carry the real rule. That prose is a cache and invites drift. One normative Feature Evidence Loop contract should own the state machine. Genesis should point to selection behavior. Tokens QA should own the Shot format and verdict. The compiler should consume outcome records without redefining acceptance.

Evidence: root CONTEXT lines 151 to 194; Genesis lines 12 to 43; Feature Compass lines 7 to 30; compiler lines 99 to 123.

Before and after

Before

Policy spread across owners

  1. Prompt prose selects and bounds an Item.
  2. Genesis parses ROADMAP and returns partial facts.
  3. Repo Context invokes Tokens QA as a subprocess.
  4. Tokens QA stores request, artifacts, costs, verdict, and context claims.
  5. The compiler separately defines request parsing, admission, proof gating, metrics, and learning.
  6. An agent correlates the documents and decides which authority wins.
Failure mode. The strongest safety rules exist, but a small model must remember them across several files. Duplicate policy increases context load and makes omission look like judgment.

After

One deep Attempt Ledger interface

  1. next(task_ref) returns one bounded Item, typed requirements, proof status, budget status, and the latest authoritative correction.
  2. record_attempt(observation) writes a minimized, local Shot with explicit provenance.
  3. record_verdict(authority) records user feedback and never infers it.
  4. close(item) deterministically checks latest accepted Shot, vetoes, and proof integrity.
  5. The context compiler consumes this interface and emits an inspectable bundle and trace.
  6. An offline learner may recommend declaration changes from reviewed pairs. A human approves each change.

Depth. Roadmap syntax, Shot ordering, cost compatibility, vetoes, proof integrity, retention rules, and next-action computation stay behind one small interface.

Smallest honest vertical slice

Use one managed Item and one real user-facing acceptance path. Run a baseline attempt and, only after a real correction, one candidate attempt. Record observed input and output tokens under the same tokenizer profile, the same acceptance criteria, the correction verbatim, proof artifacts, and the final user verdict. The candidate may change one reviewed instruction or one regression fixture.

The slice succeeds if both attempts are replayable, the candidate retains every required constraint, no veto fires, proof passes, and the user explicitly accepts it. Report the observed pair as baseline tokens / candidate tokens and baseline attempts / candidate attempts. Do not call this an improvement metric from one pair. The repository may say only that it has demonstrated the measurement path. A claim about lower median tokens per accepted result needs multiple comparable accepted Items and a predeclared analysis.

Current synthetic tests prove the state path only. The Feature Compass contract already states this limit at lines 39 to 41.

Unverified assumptions

  • No external process writes Shot feedback or mutates prompts outside the reviewed repository.
  • The CLI caller authenticates the person supplying feedback --status accepted. The local schema records authority but does not authenticate identity.
  • .audit/ is excluded from commits and publication in every relevant environment. Publication fog rules were inspected by reference, not exercised in this read-only review.
  • Token values described as observed come from trustworthy host telemetry. The repository validates shape and profile compatibility, not source authenticity.
  • No production learner exists elsewhere. This review covers the files listed in the handoff and their direct callers.

Top recommendation · strong

Make the deterministic Attempt Ledger the product, and demote “reinforcement learning” to an optional offline experiment.

Define one small interface that returns the next bounded Item, records a minimized Shot, accepts only explicit human verdicts, and closes work through deterministic proof checks. Feed its structured outcome record into the context compiler. Keep natural-language extraction and learning recommendations behind reviewable adapters with no write authority.

Short non-implementation roadmap

  1. Ratify names and owners: Feature Evidence Loop, Attempt Ledger, Context Compiler, Offline Recommender.
  2. Write one authority table for Item state, Shot state, user verdict, proof, privacy, and mutation rights.
  3. Specify the four-operation Attempt Ledger interface and error states without changing code.
  4. Split R-50 acceptance into deterministic compiler acceptance, repository migration, and optional learner evaluation.
  5. Predeclare one real two-attempt measurement slice, then collect evidence before making an improvement claim.
